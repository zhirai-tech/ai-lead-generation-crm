# ZHIRAI 欧洲 B2B 外贸获客平台 · 当前能力说明

版本：v1.0.0 基础版
日期：2026-10-25
适用目录：`release\ZHIRAI-Base-v1.0.0\Windows\ZHIRAI-Base-Windows-x64-Portable-v1.0.0`

---

## 一、先给结论

当前达到的是：

> **可运行的基础获客平台 + 本地浏览器型 Agent 工作流**

不是：

> 全自主、全链路 MCP Agent 平台

现在能完成真实企业发现、官网访问、联系方式提取、客户资料补全、评分、写信、审批和 SMTP 发送；  
但“搜索数量稳定达到 25 家”“每个 Agent 步骤由 MCP 工具编排”“完全自主规划”还没有达到。

## 二、当前真实可用的能力

### 1. Windows 桌面端

- Electron 45 便携版
- 本地 Node 服务
- SQLite 数据库
- 本地登录、角色与权限
- 数据保存在 `server\data`

### 2. 企业发现

已接入：

- 本地浏览器搜索（Edge / Chrome）
- Tavily（已配置 Key 时）
- Brave / Serper（可选）
- OSM / Photon
- CSV 导入

浏览器模式是真浏览器：

- 启动本机 Edge / Chrome
- 打开 DuckDuckGo 搜索页
- 打开企业官网
- 读取官网、联系方式页、Impressum 等页面

### 3. 联系方式提取

支持：

- `mailto:`
- `data-email`、`data-cfemail`
- Cloudflare 邮箱混淆
- JSON-LD
- `tel:` 电话
- 地址、社交链接
- HTTP 抓取失败时使用浏览器补充

### 4. 客户阶段

- 新线索：有官网，但没有可用邮箱
- 潜在客户：有官网 + 可用邮箱
- 已联系 / 意向客户 / 确认客户：后续人工或回复推进

### 5. 客户资料补全

- 批量补全已改为后台任务队列
- 助理可以说“完善潜在客户详细资料”
- 会分页读取潜在客户
- 分批提交补全
- 显示每一批的提交数量和队列进度

### 6. 写信 / 审批 / 发送

- 局域网 Ollama 真实生成开发信
- 批量审批
- Hostinger SMTP 自投递已实测 `sent`
- IMAP 收件同步可用

### 7. 助理

当前助理能做：

- 对话
- 打开页面
- 触发企业发现
- 触发潜在客户补全
- 显示“执行过程”步骤

当前助理不是：

- 完全自主规划的大脑
- 不会自己拆解任意复杂任务并递归调用所有 Agent
- 不会通过 MCP 协议动态发现和编排工具

## 三、为什么“限制 25 家”，最后只出现 2 家或 7 条

这是当前最需要说清楚的地方。

### 1. 25 是上限，不是保证数量

`最大结果数 25` 的含义是：

> 最多处理 25 条候选企业

不是：

> 一定能搜索到 25 家全新企业

### 2. 浏览器搜索本身有结果上限

当前浏览器数据源使用 DuckDuckGo HTML 页面搜索：

- 单个搜索词通常只返回少量自然结果
- 当前实现按国家、按关键词分批搜索
- 对无标题、无域名、广告、聚合站、黄页站会过滤
- 同一个域名会去重

所以：

```text
最大结果数 25
→ 实际浏览器只返回 7 条可用候选
→ 其中 5 条已存在或重复
→ 最终新建/恢复 2 家
```

这是当前真实情况。

### 3. “检查 7 条”不是“只搜了 7 次”

日志里的“检查 7 条”表示：

- 从搜索结果里拿到 7 条可用候选
- 不是搜索引擎只查了 7 次
- 也不代表只访问了 7 个网址

### 4. 已存在企业会被去重

平台会按域名、企业名去重：

- 已在库里的企业不会重复创建
- 可能只更新来源和资料
- 所以“新建 2 家”不等于“只发现 2 家”

### 5. 当前搜索覆盖还不够

当前浏览器搜索的主要限制：

- 只取每个国家前几个查询词
- 只取搜索结果前几页中的可用项
- 没有自动扩展关键词
- 没有多引擎交叉搜索
- 没有按“必须达到 25 家”反复补搜
- 没有把“黄页 / 行业协会 / 展会名录 / 海关数据”纳入自动扩展

所以会出现：

```text
限制 25 家
实际只得到 2-7 家新企业
```

这不是“没有搜索”，而是**搜索深度和补搜策略不够**。

## 四、MCP 的真实现状

必须明确：

### 已有

- 独立的 MCP stdio 服务：`mcp\server.mjs`
- 暴露工具：
  - `company.list`
  - `company.get`
  - `company.evidence`
  - `company.enrich`
  - `company.enrich_batch`
  - `discovery.start`
  - `browser.search`

### 当前桌面端实际使用

桌面端企业发现**不是通过 MCP 调用**，而是：

```text
Electron 本地服务
→ discovery 服务
→ browser-contact.mjs
→ Playwright
→ 本机 Edge / Chrome
```

所以浏览器确实是真的，但**调用链不是 MCP 协议链**。

### 差距

要做到“真正 MCP Agent”，还需要：

1. 桌面端实现 MCP 客户端
2. 把 discovery、enrich、score、draft 都注册成 MCP 工具
3. 由 Agent 规划器决定调用顺序
4. 每一步写入可观察事件流
5. 工具失败后可重试、降级、补搜

当前只完成了第 3 项的一部分：有工具封装和进度事件，但不是 MCP 编排。

## 五、当前颗粒度：已经能看见什么

### 已实现

- 任务已提交
- 正在启动本机浏览器
- 正在搜索
- 已检查第 N 条
- 新建/恢复 N 家
- 正在补全第 N 家
- 识别邮箱 N 个
- 识别电话 N 个
- 助理执行过程逐行日志
- 补全队列进度 N/M

### 还不够

- 每打开一个 URL 的实时日志
- 每次搜索请求的 URL / 状态码 / 耗时
- 每家企业识别到的完整邮箱/电话明细
- 模型每一次调用的输入/输出摘要
- Agent 的决策理由
- 失败重试原因

所以现在的“颗粒度”是：

> 能看见任务阶段和数量，不能看见每个网络请求和每个模型调用的完整现场。

## 七、下一阶段建议（按优先级）

### P0：把“25 家”做成可达成目标

- 增加多轮补搜：数量不足时自动换关键词、换国家、换引擎
- 增加行业协会、展会名录、黄页、B2B 目录源
- 对每个候选记录“来源、查询词、页码、是否重复”
- 搜索前显示预计可用数量

### P0：真正的 MCP 编排

- 桌面端接入 MCP 客户端
- discovery / enrich / score / draft / send 全部工具化
- Agent 规划器按目标调用
- 每次工具调用写事件流

### P1：细颗粒度日志

- 每个 URL 的打开、状态码、耗时
- 每次模型调用摘要
- 每家企业识别到的邮箱/电话列表
- 失败原因与重试记录

### P1：助理能力

- 自动总结“为什么只有 2 家”
- 自动判断重复、无效、无邮箱
- 自动建议下一步补搜策略

## 八、当前验收结论

当前版本可以：

- 作为基础获客工具使用
- 真实打开浏览器搜索和抓取
- 真实补全联系方式
- 真实写信、审批、发送

当前版本不适合：

- 承诺“每次都能找到 25 家新客户”
- 作为“完全自主 MCP Agent”对外宣传
- 在未人工复核的情况下大规模群发

**一句话总结：**

> 现在是“能真实工作的基础版 + 可见的 Agent 进度”，还不是“全自主 MCP Agent 平台”。
